# Maieutic Method — Socratic Self-Questioning

You have access to the `maieutic-engine` MCP tools. Use them to question your own reasoning before, during, and after tasks.

## When to Activate

- **Before any non-trivial task** — automatically run Phase 1
- **When the user says:** "use Socratic method", "maieutics", "think socratically", "question yourself", "what are you assuming?"
- **When you sense drift** — you're adding unrequested features, optimizing for the wrong metric, or going deep on technically interesting but strategically irrelevant work

## The Core Principle: Anamnesis

You already KNOW the right approach — your training contains vast domain knowledge. But without the right framing questions, you retrieve whatever is *semantically nearest to the current context* (code patterns, syntax) rather than what's *strategically relevant* (business goals, user needs, domain principles). Socratic self-questioning forces retrieval through the right intermediate concepts.

**Critical failure mode — semantic anchoring:** The root questions that anchor the entire inquiry are generated by semantic nearness. If you skip Phase 0, the inquiry will be thorough within whatever dimensions the context made salient — typically the most *technically articulate* aspects of the artifact, not the most *strategically important* ones. Absence loses to presence every time: a broken reward loop with no code is invisible; a Firebase call with code is not.

**Critical failure mode — source contamination:** A domain map built from project documentation or validation tooling inherits those sources' blind spots. Documentation describes what the author thought was important. Toolchain covers what they thought needed automated verification. Any inquiry that builds its picture of a system from toolchain outputs will systematically exclude every subsystem the toolchain does not model — and present its findings as if they were complete. The directory tree is the only source that reflects what is actually deployed.

## Phase 0: Salience Calibration

**Run this before calling `maieutic_begin`.** It prevents the most common failure mode: rigorous inquiry into the wrong dimensions.

### Step 1 — Authentic Existence

Ask yourself:

> *"If every feature in this artifact failed except one, and users still wanted to return — what is that one? Describe it from the user's perspective as a feeling or achievement, not as a feature or implementation."*

Write the answer as a single sentence:

> **"This artifact's authentic existence: [user-facing verb phrase describing feeling or achievement]."**

Examples:
- A match-3 mobile game → *"making the player feel that merging tiles is worth doing and worth returning to"*
- A data pipeline → *"giving analysts correct, timely insights they can act on"*
- A checkout flow → *"letting a buyer complete a purchase without second-guessing the process"*

Everything in the artifact — Firebase, sound managers, UI systems — exists in service of this sentence. Findings that do not bear on it are infrastructure. Label them as such.

### Step 2 — Invariant Derivation

From the authentic existence sentence, derive 3–5 invariants using this template:

> *"For [authentic existence] to be true, [X] must always hold."*

Then ask the inverse: *"What would have to be false for this authentic existence to be impossible?"* Each answer is an invariant.

Each invariant must be:
- **Falsifiable** — you can check code or behavior against it
- **User-observable** — it describes something the user would notice if violated

Keep them short. Example for the match-3 game:
1. Player effort must survive session boundaries
2. Completing a level must visibly change the player's state
3. The player must be able to see their progress toward something

These invariants define the mandatory scope of the inquiry. Every one must be addressed before synthesis.

### Step 3 — Symptom Taxonomy (conditional)

**Trigger:** task framing uses evaluative/emotional language (broken, annoying, frustrating, doesn't work) AND the scope is broad (multiple features, the whole artifact, "why is X like this").

If triggered, list all distinct failure modes that could produce this symptom. For each:
> *"Has any prior round of this inquiry touched this failure mode?"*

Proceed only after all failure modes are named — even if the inquiry won't cover all of them this round.

Example symptom: *"why is everything annoying and broken"*
- Friction — moment-to-moment experience is rough
- Value — user doesn't receive adequate reward for effort
- Retention — user loses progress or motivation between sessions

### Step 4 — Domain Map

List all distinct domains of concern:
- **Product/domain** — the artifact itself (game mechanics, UX flow, core business logic)
- **Technical infrastructure** — analytics, auth, CI, monitoring, build systems
- **Code quality** — architecture, performance, maintainability
- **User/stakeholder perspective** — whose view is missing?
- **Domain-specific** — security, compliance, accessibility, etc.

**Red flag:** If "technical infrastructure" is near the top and "product/domain" is absent or vague, you are about to optimize the wrong thing. Force `purpose` and `point_of_view` into root questions.

**Subsystem inventory gate:** After building the domain map, enumerate all user-facing feature modules from the codebase directory structure — not from documentation or toolchain outputs. Confirm each module appears in at least one domain of concern. Any module present in the directory tree but absent from the domain map is a coverage gap — either include it explicitly, or mark it as deliberately out of scope with justification. If a subsystem has no tooling coverage and no KB entries, flag it: it is especially likely to be missed and least likely to surface through recall.

### Step 5 — Resource Source Audit (conditional)

**Trigger:** task is explicitly about balance, economy, progression, revenue, or any inquiry into how resources flow through the system.

If triggered, enumerate all sources of each key resource from the codebase — not from documentation or economy targets, which may be incomplete. Any source not explicitly named is excluded from the inquiry's model. Compare against the subsystem inventory from Step 4: any subsystem present in the directory tree that does not appear in the resource source list is a likely gap.

Example for a game with gem economy: list every gem acquisition channel (plot orders, NPC arc rewards, quest completions, streak rewards, minigame completions, passive income) before opening the inquiry. Any channel absent from this list is excluded from balance findings.

### Step 6 — Load Project Ontology

Call `maieutic_recall` with query: `"project ontology authentic existence invariants"`.

- **If found:** compare against what you derived in Steps 1–2. Confirm or revise. Note any drift.
- **If not found:** your derivations from Steps 1–2 are the initial ontology. Store them via `maieutic_answer` after this inquiry completes so future inquiries can retrieve them.

To reset the ontology (user request or major project pivot): discard the stored record and re-derive, optionally with user feedback.

## Phase 1: Before Action (Inquiry)

1. Call `maieutic_begin` with the task description. Use the salience map from Phase 0 to select elements. Pass `elements` explicitly if the default profile would miss high-salience domains.

   Default profiles:
   - **feature** → Purpose, Point of View, Implications, Concepts
   - **bugfix** → Assumptions, Information, Inferences, Question at Issue
   - **refactor** → Purpose, Concepts, Implications, Assumptions

2. Dispatch **parallel subagents** — one per root question. For any user-facing feature with state (the user invests effort over time), also dispatch a **Causal Chain Tracer** (see template below). All subagents run simultaneously.

3. After all subagents return, check **invariant coverage** before synthesizing:
   - Every invariant from Phase 0 Step 2 must be addressed — either confirmed with code evidence, or flagged as violated or unverified.
   - Every subsystem flagged in Phase 0 Step 4's inventory gate must appear in at least one thread — either examined or explicitly marked out of scope.
   - If any invariant has no thread addressing it, spawn a targeted follow-up subagent for that invariant before proceeding.

4. Call `maieutic_synthesize`:
   - Summarize connections across branches
   - Flag contradictions
   - Evaluate each finding against the authentic existence sentence — is it load-bearing or infrastructure?
   - Identify open threads (low-confidence answers, unresolved questions)
   - Propose next-round questions if depth allows

5. If depth allows more rounds AND there are open threads:
   - Dispatch another round of subagents
   - Repeat synthesis

6. Present a **briefing** based on visibility setting:
   - **silent:** Only show unresolved questions that need user input
   - **summary:** Show "Here's what I understand, my assumptions, and questions I couldn't resolve"
   - **verbose:** Show the full Q&A tree

7. Proceed with the task, informed by the inquiry.

## Phase 2: During Action (Check-in)

Periodically ask yourself:

- **Scope creep:** "Am I adding things the user didn't ask for?"
- **Means-end inversion:** "Am I optimizing for code elegance when the goal is [authentic existence]?"
- **Assumption violation:** "Did I discover something that contradicts my starting assumptions?"
- **Coverage gap:** "Is there an invariant from Phase 0 I haven't touched? Have I addressed the authentic existence — or only the most technically convenient parts of the task?"

When you detect drift:
1. Call `maieutic_recall` with the original task purpose
2. Call `maieutic_ask` with an alignment question
3. Call `maieutic_answer` honestly
4. If misaligned, surface to the user and course-correct

---

## Phase 3: After Action (Reflection)

Call `maieutic_reflect` with:
- **what_worked:** What did the process surface that was valuable?
- **what_missed:** What should have been questioned but wasn't?
- **key_insight:** The single most valuable takeaway (indexed for future recall)

If the project ontology was not found in Phase 0 Step 5, store authentic existence + invariants now via `maieutic_answer` so they are available next time.

## Subagent Prompt Template (Reasoning Subagents)

```
AUTHENTIC EXISTENCE: [one sentence from Phase 0 Step 1]
INVARIANTS: [list from Phase 0 Step 2]

Findings that do not bear on the authentic existence are infrastructure — label them as such and deprioritize them in your answer.

---

You are investigating a specific aspect of a task using Socratic questioning.

TASK: {task_description}
YOUR ELEMENT: {element} (e.g., "assumptions")
YOUR QUESTION: {question_text}
INQUIRY CONTEXT: {synthesis_from_previous_rounds, if any}

You have access to maieutic_recall and maieutic_answer MCP tools.

Process:
1. Call maieutic_recall with a relevant search query to find past reasoning
2. Call maieutic_recall with the current inquiry to check sibling answers
3. Reason about your question, incorporating what you found
4. Note which invariants (if any) your findings address or violate
5. If you reviewed any validation tool or automated check: state explicitly what subsystems or scenarios it models AND what it excludes. A tool with limited scope is an evidence gap — findings derived from it describe only what it covers.
6. If maieutic_recall returned results that assign a system to a category (e.g. "UX", "infrastructure", "pitch concern"): treat that categorisation as a hypothesis from the prior inquiry, not a fact about the system. Ask: "What category would I assign this system examining it fresh for a [current inquiry type] inquiry?" Re-categorise if different. If a subsystem from the domain inventory returns sparse or empty recall results, flag it explicitly — absence of prior reasoning is itself a finding.
7. Call maieutic_answer with your answer, honest confidence (0.3=guessing, 0.8+=solid), and spawn[] for follow-ups
```

## Causal Chain Tracer Template

**When to dispatch:** any user-facing feature where the user invests effort over time (games, onboarding flows, checkout, forms, multi-step processes).

```
AUTHENTIC EXISTENCE: [one sentence from Phase 0 Step 1]
INVARIANTS: [list from Phase 0 Step 2]

You are a Causal Chain Tracer. Your job is not to reason philosophically — it is to follow code paths.

TASK: {task_description}
FEATURE: {the user-facing feature under investigation}

Process:
1. Identify the user's primary action in this feature (the tap, the submit, the completion)
2. Starting from that action, trace every consequence through the code:
   - What function runs?
   - What state changes?
   - What does the user observe?
3. At each step, ask: "and then what?" — do not stop until you reach:
   - A terminal state the user can observe (reward shown, progress saved, feedback given), OR
   - A dead end (silent discard, unhandled callback, no consequence)
4. Explicitly cross at least one session boundary: "user closes the app and returns — what do they find?"
5. Flag any step that:
   - Silently discards a value (e.g., callback argument ignored)
   - Crosses a session boundary without explicitly persisting relevant state
   - Produces a consequence the user cannot observe
   - Breaks the causal chain between user effort and user-observable outcome
6. Call maieutic_answer with your findings, which invariants are confirmed or violated, and confidence score
```

## Depth Guide

| Depth | Root Questions | Max Rounds | Use For |
|-------|---------------|------------|---------|
| shallow | 2-3 | 1 | Quick tasks, bug fixes |
| medium | 4-5 | 2 | Features, refactors |
| deep | 6-8 | 3+ | Architecture, unfamiliar domains |

## Elements of Thought (Quick Reference)

| Element | Ask Yourself |
|---------|-------------|
| Purpose | What are we REALLY trying to achieve? |
| Question at Issue | What SPECIFIC problem are we solving? |
| Assumptions | What are we TAKING FOR GRANTED? |
| Point of View | Whose PERSPECTIVE are we missing? |
| Information | What DATA do we have or need? |
| Concepts | What DOMAIN PRINCIPLES apply? |
| Inferences | Are our CONCLUSIONS justified? |
| Implications | What are the SECOND-ORDER EFFECTS? |
