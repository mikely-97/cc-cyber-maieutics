# Proposal: Symptom-Framing Blind Spot in Phase 0 Salience Calibration

**From:** Claude (game designer role, Obliq project)  
**Date:** 2026-04-05  
**Status:** Proposal — not a prescription. The context below is specific to game design; the maintainers should judge whether it generalises.

---

## What This Is

I am writing this as a game designer who just used the maieutic skill on a player-facing feature analysis and had two financially consequential issues slip past a multi-round, 15-agent inquiry. I am not proposing changes to the skill directly — the skill is used across many domains and I am not qualified to reason about all of them. I am describing what failed in my domain, why I believe it is a structural issue in Phase 0, and proposing additions with the explicit note that the maintainers should decide how general they are.

---

## What Failed

The task: investigate all three minigames in Obliq (a mobile merge/event game) to find "why everything is annoying and broken."

The inquiry ran deep (3 rounds, ~15 subagents) and found 10+ real issues: silent failure states, missing feedback, door tile discoverability, invisible level-complete moments. All of these were correct finds. The inquiry was thorough within its scope.

What it missed:

1. **Match-3 board state is not persisted across sessions.** Level index saved; board regenerated from seed on re-entry. A player who leaves mid-level returns to a blank board. All invested effort lost.

2. **No direct reward on level completion.** The `onComplete` callback receives a score integer and passes it to `(_) {}` — silently discarded. All value routes through a distant milestone bar. The effort→reward loop has a broken link.

These were found immediately when the user asked two plain English questions: "What happens when you exit and come back?" and "What reward do you get for completing a level?" Neither question was ever generated by the inquiry.

---

## Root Cause

### The task description was emotionally framed

> *"why is all of this annoying as hell, broken and doesn't work"*

This is symptom language. It does not name a failure mode — it names a feeling. The most semantically adjacent interpretation in a code-heavy context is **friction**: missing sounds, silent failures, bad UI signals. That interpretation is correct and produced correct answers. But it is not the only interpretation, and in a monetized game it may not even be the most important one.

Three distinct failure modes can produce "this feels broken and annoying":
- **Friction** — moment-to-moment experience is rough
- **Value** — player doesn't understand or receive adequate reward for effort  
- **Retention** — player loses progress between sessions; doesn't want to return

The inquiry covered friction comprehensively. It never asked about value or retention.

### Phase 0's red flag rule was present but not enforced

The skill says:

> *"If 'technical infrastructure' is near the top of your domain map and 'product/domain' is absent or vague, you are about to optimize the wrong thing."*

The equivalent red flag for my situation — "if the task is framed as a symptom and the most salient domain is friction/code, check that you've also asked about value and retention" — does not exist. The red flag in the skill is about infrastructure vs. product. My failure was product-friction vs. product-value: both inside "product/domain," so the existing red flag didn't catch it.

### The knowledge base had no prior anchors on these concepts

The maieutic engine generates questions by semantic nearness to the task description. Because prior inquiries for this project also focused on friction (sounds, UI, balance), the knowledge base contained no recalls about reward chains or persistence. No past reasoning pulled the inquiry toward those dimensions.

## What I Propose

I am proposing additions, not rewrites. The existing Phase 0 logic is correct and valuable. These are additive probes for specific task types.

### Proposal 1: Symptom framing detection

When the task description contains evaluative/emotional language (broken, annoying, frustrating, useless, doesn't work, trash), add a mandatory pre-flight step before element selection:

> **Name the failure taxonomy.** List the distinct failure modes that could produce this symptom. For each, ask: "Has any prior round of this inquiry touched this failure mode?" Proceed only after all modes are named, even if the inquiry won't cover all of them.

This is domain-agnostic. Emotional task framing is always a symptom description. The failure modes vary by domain, but the discipline of naming them before anchoring is universal.

**Game design instantiation:**
- Friction (moment-to-moment experience)
- Value (what the player receives for effort)
- Retention (what survives session boundaries)

**Software engineering instantiation (for comparison):**
- Correctness (code does the wrong thing)
- Performance (code does the right thing too slowly)
- Reliability (code does the right thing until it doesn't)

The maintainers should judge whether to encode a generic version or leave this as domain-specific guidance in downstream skill derivatives.

---

### Proposal 2: Value chain and persistence as first-class inquiry topics for stateful user-facing features

For any feature that involves: (a) a player/user taking repeated actions over time, AND (b) state that could either be saved or discarded between sessions — the following two questions should be injected as root questions regardless of element selection:

> 1. **Value chain:** "What does the user tangibly receive for completing this action/session? Trace every step from the triggering event to the user's inventory/state. Is any link discarded, ignored, or routed through an abstraction the user cannot see?"

> 2. **Persistence:** "What state survives a session boundary for this feature? What is regenerated? Could a user lose invested effort by closing the application and returning?"

**Why these are not covered by the standard 8 elements:**

The standard elements reason about *the task at hand* — its purpose, assumptions, implications, etc. These two questions reason about the *feature as a system over time* — its reward loop and its memory. They are data-flow questions, not reasoning questions. The standard elements do not force you to trace code paths; they force you to examine your own thinking. That distinction is why these slipped through even a deep inquiry.

**Scope:** I believe these apply to any stateful user-facing feature, not only games. A form that loses progress on navigation, a checkout that resets on error, an onboarding that forgets where you were — all are persistence failures. A feature that completes but shows no confirmation, an API that returns a result the caller silently discards — all are value chain failures.

The maintainers should decide the right trigger condition. In my domain it is: "player-facing mechanic with sessions." The general trigger might be: "user-facing feature with state that persists beyond a single interaction."

---

### Proposal 3: Post-inquiry completeness check against stated failure modes

After synthesis, before presenting the briefing: verify that the inquiry touched every failure mode named in the pre-flight taxonomy (Proposal 1). If a failure mode has no answered question, spawn a follow-up agent before concluding.

This closes the loop: even if the inquiry drifted into one failure mode, the completeness check forces the gap to surface before results are presented.

---

## Evidence

**From the Obliq knowledge base (via maieutic_recall):**

Searching "reward completion level player value" returns 55KB of results — every answer is about feedback signals (sound, UI, visual). The phrase "what does the player receive for completing" does not appear in any answer.

Searching "session persistence state exit re-entry board save" returns 76KB of results — every answer is about the entry moment (what the player knows before their first tap). "What happens when they come back?" was never asked as a follow-up thread.

The knowledge base accurately reflects what was asked. This is an input-framing problem, not an answer-quality problem.

---

## What I Am Not Proposing

- I am not proposing game-specific language be added to the general skill. The examples above are illustrations, not prescriptions.
- I am not proposing the existing Phase 0 logic be changed. It is correct. The proposals above are additive.
- I am not proposing that every inquiry cover value chains and persistence. Only those where the trigger condition is met.
